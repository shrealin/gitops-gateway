# 第一次来？先读这页

你不用先学会所有云技术。先记住一件事：**要改变公司的云资源，先找到负责这件事的仓库，写清需求，经过审查后再执行。**

GitHub 在这里既是存放配置的地方，也是提出申请、讨论方案和留下记录的地方。阿里云则是账号、网络、服务器等资源真正运行的地方。

## 先认识三个词

| 名称 | 可以怎样理解 |
| --- | --- |
| 仓库（Repository） | 某一类工作的专用文件夹，里面放配置、说明和变更记录 |
| PR（Pull Request） | 一份“变更申请单”，让别人看到你想改什么，并进行审查 |
| 工作流（Workflow） | 根据申请运行的一组自动步骤，例如检查配置、预览变化、执行变更 |

把“用 GitHub 中经过审查的配置管理资源”这种做法称为 **GitOps**。这份指南会优先说具体该做什么，其他词可以随时查[词语解释](./glossary)。

## 一次普通变更怎么走？

1. **找到地方。** 先查[办事指南](./requests)，确认这件事应该去哪个仓库。
2. **写清需求。** 说明为什么需要、涉及哪个部门和环境、会影响谁。不确定的地方直接写明。
3. **形成申请。** 由你或协助你的维护者修改相应配置，提交 PR。
4. **看预计影响。** 自动流程会检查配置，并尽可能展示执行后会新增、修改或删除什么。这个预览叫 plan。
5. **请维护者审查。** 检查申请目的和预览是否一致，通过后合并。若仓库还设置了环境审批，需要继续完成相应审批。
6. **确认执行结果。** 看自动执行是否成功，再检查实际效果。记录验证结果，才算办理完成。

::: tip 审查、合并、执行成功，是三个不同节点
有人批准了 PR，并不代表已经合并；已经合并，也不保证云端执行一定成功。查看仓库的 **Actions** 页面，找到对应变更的运行记录。
:::

## 不会改代码，也可以把申请准备好 {#first-pr}

打开目标仓库，先读首页说明。已有配置模板时，维护者可以根据你的需求补齐内容。支持 Issues 的仓库，也可以先开一条讨论需求的 Issue，再由维护者将确认的方案写入 PR。

**最终资源变更仍要落实到配置 PR。** Issue 是需求记录，不会直接开通账号、授权或分配地址。

你可以把下面的内容复制到对应私有仓库中，填写后交给维护者。本站是公开指南，不接收含有内部细节的业务申请：

```text
我想办的事：
所属公司 / 部门 / 系统：
业务负责人：
为什么需要：
涉及环境：测试 / 生产 / 待确认
希望新增或调整的内容：
可能影响的系统：
怎样确认已经完成：
期望时间及原因：
相关申请或讨论链接：
```

如果你会修改配置，可以在目标仓库中创建工作分支，完成修改后打开 **Pull requests → New pull request**，提交到 `main`。申请里写清上述信息，并根据检查和审查意见继续修改。

当前云端预览需要使用目标仓库内的分支；从个人复制仓库（Fork）提交的 PR 不会得到云凭证。没有仓库写入权限时，请维护者协助，不要将长期云密钥填入申请。

## 测试环境和生产环境怎么选？

**测试环境（test）** 用来验证方案；**生产环境（prod）** 承载正式业务。它们有各自的账号、授权和资源记录。

申请时需要明确环境。测试环境通过了，并不会自动得到生产授权或生产资源。尤其是网络地址，当前流程要求先完成测试申请和验证，再提交单独的生产申请。

## 用一个业务团队举个例子

假设一个业务团队要建设新系统：

| 你走到哪一步 | 下一步去哪里 |
| --- | --- |
| 还没有适合的云账号 | 去账号申请仓库；已有账号时先确认归属与用途 |
| 有账号，但业务仓库还不能部署 | 去账号基线仓库，申请仓库与环境的授权 |
| 需要创建业务网络 | 去共享网络仓库，申请对应环境的地址 |
| 准备创建服务器等资源 | 在对应业务仓库提出资源变更；首次使用先确认完成接入 |
| 希望访问另一个部门的系统 | 再向共享网络仓库提出互联需求，双方一起确认方案 |

这些步骤不会自动互相代办。每完成一步，保留对应 PR 和执行结果链接，作为下一步的依据。

## 遇到问题时找哪里？

| 看到的情况 | 先检查什么 |
| --- | --- |
| 仓库链接显示 404 | 关联仓库目前为私有仓库，先确认登录账号有访问权限 |
| PR 一直在等待 | 看是在等审查、环境审批，还是自动检查完成 |
| 提示没有云账号操作权限 | 找账号基线维护者，核对仓库、环境和目标账号的对应关系 |
| 找不到已申请的地址 | 找共享网络维护者，核对环境、地址登记和实际执行结果 |
| 已合并，但资源没有变化 | 查看 Actions 执行记录；不要只看 PR 的合并状态 |
| 检查规则或执行流程有问题 | 查看公共工作流仓库的说明，再由维护者确认处理方式 |
