# 我要办什么事

先按事情选择仓库，再准备申请内容。**每份申请都应说清：为什么做、谁负责、改哪个环境、怎样确认完成。**

本页是公开说明。填好的申请和具体账号、地址、访问需求，请提交到对应私有仓库，不要发在本站的公开 Issue 或 PR 中。

| 事情 | 对应入口 |
| --- | --- |
| 新建部门或系统的云账号 | [申请云账号](#account) |
| 让仓库可以操作云账号 | [开通部署权限](#identity) |
| 新建网络前登记地址 | [申请内网地址](#network) |
| 创建或调整服务器、网络、存储等 | [变更业务资源](#resources) |
| 两个系统需要互相访问 | [申请网络互联](#connect) |
| 改善公共流程或提出统一规则 | [改进流程与规则](#standards) |

## 申请一个云账号 {#account}

**去 [alicloud-account-vending-machine](https://github.com/shrealin/alicloud-account-vending-machine)。** 它负责在公司的阿里云组织下创建子账号。

准备所属公司、部门、系统名称、用途、业务负责人，以及测试或生产环境。已有账号时，先确认是否适合当前用途，避免重复申请。

1. 和仓库维护者确认账号归属及命名。
2. 修改账号声明并提交 PR，审查拟创建的账号和组织位置。
3. 合并后检查自动执行结果，确认创建成功和账号信息。
4. 将账号信息交给[部署权限接入](#identity)的下一步申请。

**完成标志：** 账号已实际创建，归属和用途已确认。业务仓库的权限仍需单独配置。


## 让仓库可以部署到云账号 {#identity}

**去 [iac-alicloud-account-baseline](https://github.com/shrealin/iac-alicloud-account-baseline)。** 它负责建立“业务仓库 → 运行环境 → 目标子账号”的授权关系。

准备仓库完整链接、目标账号、环境名称和负责人。例如，同一业务的测试与生产环境，需要分别对应正确的账号。

1. 确认子账号已存在，并明确仓库与环境的对应关系。
2. 提交基线配置 PR，维护者核对身份和目标账号。
3. 合并并执行后，获取对应部署身份和基础存储的配置信息。
4. 在业务仓库建立相应 GitHub Environment，设置所需变量、分支限制和审核规则，再接入公共工作流。
5. 运行检查，确认操作的是预期环境和账号。

**完成标志：** 指定仓库在指定环境中可以使用临时凭证完成所需操作。只合并基线配置，还不能说明业务仓库的设置已经完成。


## 申请一段内网地址 {#network}

**去 [iac-shared-network](https://github.com/shrealin/iac-shared-network)。** 使用受统一管理的内网地址前，必须先在这里登记。具体范围仅在私有仓库中查看。

准备组织归属、系统用途、负责人、预计规模、部署环境、地域，以及是否需要与其他系统互通。不确定网段大小时，先描述需求，请维护者协助选择。

1. **提出地址方案。** 由维护者确认合适的地址范围，并检查是否与已有地址冲突。
2. **提交测试 PR。** 在共享网络测试配置中新增或启用分配，审查后合并并执行。
3. **完成验证。** 确认地址记录存在、业务能够正确使用，且不会干扰现有系统；在申请中留下验证结果。
4. **单独提交生产 PR。** 引用测试申请和验证结果，把相同的地址段及组织路径同步到生产配置。
5. **确认生产生效。** 生产申请审查、合并、执行成功后，业务生产环境才能使用对应地址。

**完成标志：** 所需环境的地址分配已经实际登记，并完成相应验证。PR 获批、合并或地址写在规划图里，都不能单独作为已可使用的证明。



## 创建或调整业务资源 {#resources}

**去所属业务或系统的基础设施仓库。** [iac-leasing-team](https://github.com/shrealin/iac-leasing-team) 是一个业务仓库入口示例。请向内部维护者确认你的项目对应哪个仓库。

准备资源需求、用途、负责人、涉及环境、可能影响的系统，以及验证和恢复安排。新建网络时，还要附上已批准且生效的地址记录。

1. 确认账号、部署权限和所需地址已经准备好。
2. 首次使用时，由维护者确认业务仓库已完成初始化、环境配置和公共工作流接入。
3. 在业务仓库提交配置 PR，检查自动生成的新增、修改和删除预览。
4. 维护者审查并合并后，确认自动执行成功。
5. 检查业务功能和资源状态，把验证结果留在记录中。

**完成标志：** 资源达到预期状态，相关业务验证完成。删除资源时，还应确认数据备份和下游依赖。


## 让两个系统互相访问 {#connect}

**去 [iac-shared-network](https://github.com/shrealin/iac-shared-network) 提出互联需求。** 未来计划用阿里云 CEN 来集中声明跨部门、跨系统的网络连接。

准备双方系统及负责人、账号、地域、已登记网段、访问方向、服务端口、业务原因，以及期望的验证方式。

1. 双方负责人先确认互通范围和必要性。
2. 在共享网络仓库记录需求，维护者评估互联、路由和访问规则等方案。
3. 因为 CEN 配置目前尚未建设，需要先完成实现，再按方案提交配置 PR、审查并执行。
4. 双方验证允许的访问确实通畅，不需要开放的访问仍被限制，并记录结果。

**完成标志：** 具体互联配置已实现、执行并通过验证。地址不冲突，不代表网络已经连通；创建连接也不代表所有业务访问规则都已配置好。

## 改进公共流程或统一规则 {#standards}

这两类需求分别有自己的入口：

| 你要改什么 | 去哪里 | 需要说明 |
| --- | --- | --- |
| 检查、预览、执行的步骤 | [iac-shared-tools](https://github.com/shrealin/iac-shared-tools) | 原流程有什么问题、预期如何运行、哪些调用仓库受影响 |
| 公司要求所有资源变更遵守的规则 | [policy-library-shrealin](https://github.com/shrealin/policy-library-shrealin) | 为什么需要、允许的例子、不允许的例子、适用范围 |

公共流程变更应先验证，再确认调用方使用的版本和影响范围。具体引用方式请在私有仓库内核对。

统一规则检查仍待建设。新增规则还需要在公共工作流中加入 OPA 检查并验证，**把规则文件放进仓库，并不会使所有变更立刻受到约束。**

## 可复制的申请说明 {#template}

下面是通用说明模板。请复制到对应私有仓库中填写，按事项补充必要信息，不必为了填写模板去猜不确定的内容。

```markdown
## 我想做什么
<!-- 新增 / 调整 / 删除什么，为什么需要 -->

## 归属和负责人
- 公司 / 部门 / 系统：
- 业务负责人：
- 目标仓库：
- 目标账号和环境：

## 具体需求
- 期望结果：
- 涉及地址 / 资源 / 权限：
- 可能影响的系统：
- 期望时间及原因：

## 如何确认完成
- 验证方式：
- 如果失败，如何恢复或停止影响：
- 尚待确认的问题：

## 相关记录
- 前置申请 PR：
- 测试验证结果（申请生产时填写）：
```

申请中的账号标识、资源说明应放在有相应访问权限的业务仓库里；无需在本站额外复制，也不要填写长期密钥。
