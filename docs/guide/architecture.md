# 各环节如何配合

这套体系把资源管理分成几件边界清楚的工作：**准备账号、授予部署权限、分配网络地址、执行资源变更，以及统一维护规则。** 每件事都有自己的仓库，维护者通过申请和执行记录把它们连接起来。

GitHub 保存“我们希望资源是什么样”，阿里云承载实际资源，自动流程负责把经过审查的配置变成实际结果。本页讲解协作机制，内部账号、权限明细和部署情况请在私有仓库中查看。

## 仓库之间如何连接？ {#relationships}

### 账号申请 → 账号基线：先有空间，再决定谁能操作

账号申请仓库按照阿里云 Landing Zone 的管理思路创建子账号。Landing Zone 可以理解为使用云服务前搭好的组织和管理基础。

账号准备完成后，基线仓库建立授权。它需要知道目标业务仓库、运行环境和账号之间的对应关系。**创建账号本身不会自动完成仓库接入。**

这就像先准备一间工作室，再确定哪些人有权进入。两件事分开确认，便于日后新增项目、调整权限和处理环境变化。

### 账号基线 → 业务仓库：领取本次运行的临时通行证

工作流运行时，GitHub 提供身份凭据。阿里云检查它是否来自获准的仓库和环境，核验通过后才发放短期操作凭证。

可以理解为：**凭工作身份领取当次通行证，按允许的范围办事，过期后失效。** 业务仓库因此无需保存一把长期有效的云账号钥匙。

身份核验叫 **OIDC**，代表权限的身份叫 **RAM Role**，临时凭证由 **STS** 发放。“无需长期密钥”不表示无需权限管理；谁能进入、进入后能做什么，仍需要分别配置和审查。

具体身份、信任条件和权限范围保留在基线私有仓库中。GitHub 上的分支和环境审批设置，也由维护者按实际约定配置。

### 共享网络 → 业务仓库：先登记门牌号，再建网络

共享网络仓库集中登记受管理的内网地址。申请成功并实际生效后，业务仓库读取对应环境的分配，用来创建业务网络。

读取地址信息，不等于可以修改其他业务的分配。读取权限和部署权限需要分别按用途安排。

新建业务网络因此至少依赖两项准备：**部署授权已经完成，对应环境的地址登记已经生效。** 地址登记不会自动创建业务资源，也不会自动连通两个网络。

### 业务仓库 → 公共工作流：业务写需求，共用步骤负责执行

业务仓库描述“需要什么资源”，并引用公共工作流。公共工作流负责检查配置、生成变更预览，以及在日常 PR 合并流程中执行已经审查的计划。

不同业务可以保留各自的资源安排，同时使用一致的检查和执行方式。公共流程改进时，也能在统一入口讨论、验证和发布。

调用哪个版本、需要哪些前置设置，以公共工作流及调用仓库的私有说明为准。集中维护不等于所有仓库总会自动更新到同一版本。

### 统一策略库 → 公共工作流：未来加入规则检查

未来，公共工作流会将变更预览交给 OPA 检查。OPA 可以理解为“按照统一规则核对申请内容的程序”，规则集中放在策略库。

比如一项共同要求需要自动核对，就可以为它编写规则，并给出通过和不通过的例子。规则库和工作流接入需要一起验证，**规则写进仓库，并不等于已经对所有变更生效。** 这项能力目前仍待建设。

## 一次日常变更，实际发生什么？ {#daily-flow}

假设一个业务团队要为新系统增加资源：

1. **提出变更。** 在自己的业务仓库修改配置并提交 PR，说明用途和预期影响。
2. **自动检查。** 公共工作流检查配置是否符合约定、是否能被工具正确读取。
3. **生成预览。** 工作流取得相应环境的临时凭证，计算会新增、修改或删除什么，供维护者查看。
4. **人工审查。** 维护者核对业务目的、影响范围和预览，通过后合并。
5. **核对并执行。** 工作流确认执行内容与已审查的计划一致，再操作对应账号中的资源。
6. **确认结果。** 检查执行记录，完成业务验证，把结果留在私有申请中。

测试和生产分别处理。自动流程能帮忙检查和执行，但不能替代业务验证，也不能仅凭运行成功就证明某个生产方案已经通过测试。需要分阶段推进的申请，应按约定拆成独立 PR。

### 如果需要日常流程之外的操作呢？ {#manual-run}

先在相应私有仓库中与维护者确认原因、范围、执行方式和验证安排，并留下记录。具体操作入口以仓库内部说明为准。普通申请仍按上面的 PR 路径办理。

## 为什么这样设计？ {#why}

### 让资源归属清楚，减少相互影响

不同业务和环境使用对应账号，便于确认资源由谁负责。测试与正式业务分开处理，可以降低误操作影响其他资源的机会。实际隔离效果仍取决于权限和网络配置。

### 把“开账号”和“给权限”分开

账号可能已经存在，但不是每个仓库都应该能操作它。分开管理这两件事，方便审查新仓库接入、环境变化和权限调整。

### 让团队专注业务，让共同做法集中改进

业务资源由最了解需求的团队维护。共用的检查和执行步骤放在公共仓库，减少各团队重复维护流程造成的差异。公共流程的调整则需要考虑调用方，做好验证和版本管理。

### 提前避免地址冲突

两个网络暂时独立，未来也可能需要互通。如果使用了重叠地址，连接就会更复杂。统一登记能提前减少这类问题，为扩展留下空间。

具体地址和分配关系属于内部配置，不在本公开站点展示。

### 让每一次改变都能说明原因

PR 把需求、配置、审查意见和变更预览放在同一个地方。出现问题时，维护者可以沿着记录查到变化的来由，再决定怎样处理。

这不是“一键撤销”。撤回配置可能再次修改或删除资源，涉及数据时还需要备份、恢复方案和重新审查。
